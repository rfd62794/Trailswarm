# Building on a mature Pokemon RAM ecosystem

Public work already covers most of what a Trailswarm RAM/ROM toolkit needs to read, and almost none of what it needs to write. **Reading is a solved, well-documented problem**: the pret/pokered disassembly gives authoritative WRAM labels, community RL projects have converged on a small stable address set, and an RGBDS `.sym` file plus a stable-retro-style typed variable file is the de facto vocabulary for retro RAM tooling. **Writing is thin**: PyBoy ships an experimental two-instance serial cable that is demonstrated for Gen 1 trading only, and no published project automates Colosseum battles, injects an arbitrary opponent party through PyBoy, or reads a shared world map of NPCs across agents. The strongest reusable design for shared-map visualisation is pokerl-map-viz, which needs only `[x, y, mapId]` per agent. The recommended shape is a small, versioned address-table layer generated from pokered symbols, a typed reader on top, a separate presentation/bridge layer, and two experimental write paths (link and injection) that need a spike before commitment. Gaps remain in licences, exact Gen 1 wire protocol bytes, and several unread pages, flagged below.

## The authoritative sources are the disassembly, not the wikis

pret/pokered is the canonical buildable disassembly (about 5k stars, 2,836 commits), building bit-identical Red and Blue ROMs, with WRAM labels in `ram/wram.asm` ([pret/pokered](https://github.com/pret/pokered)). Symbol files are not in the master tree; the README points to a separate `symbols` branch ([pret/pokered](https://github.com/pret/pokered)). The file format is RGBDS `.sym`: one `<bank>:<address> name` per line in unprefixed hex, `;` comments, and the spec itself admits it "was always loosely defined, leading to subtle incompatibilities" ([RGBDS sym format](https://rgbds.gbdev.io/sym)). The pokerl documentation shows the practical use, with lines such as `00:d16c wPartyMon1HP`, and warns that labels pointing into ROM cannot be read as RAM and instead need a hook at the nearest label ([pokerl: Reading RAM](https://drubinstein.github.io/pokerl/docs/chapter-3/reading-asm)). PyBoy's constructor accepts a `symbols=` argument and exposes `symbol_lookup` and `hook_register(bank, addr, callback, context)` ([PyBoy API](https://docs.pyboy.dk/api/pyboy.html)), though whether `symbols=` consumes pokered's `.sym` unmodified was not confirmed.

The community wikis are a cross-check only. Data Crystal's Red/Blue RAM map is broad (party count `D163`, six 44-byte party structs from `D16B`, map `D35E`, player Y/X `D361/D362`, badges `D356`, sprite tables `C100-C1FF`/`C200-C2FF`, missable-object flags `D5A6-D5C5`) but is flagged "To do", contains overlapping ranges, typos such as "DC65-CC66", addresses listed with two meanings, and "Level" bytes that are not the real level ([Data Crystal RAM map](https://datacrystal.tcrf.net/wiki/Pok%C3%A9mon_Red_and_Blue/RAM_map)). The agent projects agree with it on core addresses: PokemonRedExperiments uses `0xD163` for party size, `0xD35E` for map, `0xD362/0xD361` for X/Y, `0xD356` for badges and `0xD747-0xD886` for event flags ([memory_addresses.py](https://raw.githubusercontent.com/PWhiddy/PokemonRedExperiments/master/baselines/memory_addresses.py)). Those projects hard-code addresses by hand rather than loading `.sym` ([red_gym_env.py](https://raw.githubusercontent.com/PWhiddy/PokemonRedExperiments/master/baselines/red_gym_env.py)), which is the pattern to improve on. For the toolkit this means generating the address module from a pinned pokered `symbols` commit, asserting ROM revision on load, and unit-testing the table against a known save state. Bulbapedia's Gen I structure pages returned HTTP 403 during research, so party/box/trainer struct field offsets and species-index details remain unverified against that source.

Save-file tooling is a secondary route. PKHeX has a UI-independent `PKHeX.Core` with Gen 1 support ([kwsch/PKHeX](https://github.com/kwsch/PKHeX)), but saves update only on in-game save, so they are not a live source; the one Python Gen 1 save parser found (`emberquill/pkmn-gen1`) was archived on 2026-02-05 ([Codeberg](https://codeberg.org/emberquill/pkmn-gen1)). Its struct definitions are still useful because party and box mon layouts largely match WRAM (an inference from the notes, not verified against source).

## What agent projects actually read, and the standards worth adopting

The proven minimal agent state is small: map, X, Y, party species/HP/level, badges, money, event flags and opponent levels. PokemonRedExperiments (MIT) reads exactly these, including 2-byte big-endian HP at `0xD16C, 0xD198, ...` and opponent party levels at `0xD8C5, 0xD8F1, ...` ([memory_addresses.py](https://raw.githubusercontent.com/PWhiddy/PokemonRedExperiments/master/baselines/memory_addresses.py)). pokemonred_puffer adds a reusable named-event table: `data/events.py` maps the 320 bytes from `0xD747` to named bit fields via ctypes ([events.py](https://raw.githubusercontent.com/drubinstein/pokemonred_puffer/main/pokemonred_puffer/data/events.py)), but the repository shows no licence, so it is a design reference, not code to copy ([pokemonred_puffer](https://github.com/drubinstein/pokemonred_puffer)). LLM harnesses go further and decode RAM into text and maps: Gemini Plays Pokemon pulled game state and text out of RAM and added a textual minimap and grid overlay ([dbreunig](https://www.dbreunig.com/2025/06/17/an-agentic-case-study-playing-pok%C3%A9mon-with-gemini.html)), and the Continual Harness paper (which evaluates Red and Emerald) exposes party, inventory, map ID, dialogue and battle status through a memory reader, rendering an ASCII map of walkable tiles, interactables, NPCs, ledges and player facing ([arXiv 2605.09998](https://arxiv.org/html/2605.09998v1)). That harness publishes no addresses or repo link, and the NeurIPS PokeAgent Challenge speedrun track used Emerald, so its reader is not reusable for Gen 1 ([arXiv 2603.15563](https://arxiv.org/abs/2603.15563)).

Beyond Pokemon, three standards matter. First, stable-retro (the Farama successor to the now-archived gym-retro, archived 2026-05-29) defines the RL convention: `data.json` with name, `address` and a struct-like `type` string (endianness, then `i`/`u`/`d`/`n` for signed, unsigned, BCD, nibble-BCD, then byte count, e.g. `|u1`, `>u2`, `>d2`), plus `scenario.json` for reward and done conditions ([stable-retro integration docs](https://stable-retro.farama.org/integration/), [openai/retro](https://github.com/openai/retro)). Game Boy is supported there. Second, AtariARI shows the wrapper pattern: a per-game address table producing `info["labels"]` with semantic variables, though its table is Python code rather than data ([AtariARI](https://github.com/mila-iqia/atari-representation-learning)). Third, RetroAchievements supplies the richest crowd-sourced vocabulary: code notes attached to addresses, 8/16/32-bit, single-bit and nibble sizes, and a flattened address space for GBC banked WRAM ([RA Memory Inspector](https://docs.retroachievements.org/developer-docs/memory-inspector.html), [RA Console Specific Tips](https://docs.retroachievements.org/Console-Specific-Tips/)). Cheat and watch formats (GameShark, BizHawk `.wch`, RetroArch `.cht`) are low-fidelity and untyped; GameShark in particular is a single write-byte primitive, and PyBoy implements only type 01 ([Pan Docs](https://gbdev.io/pandocs/Shark_Cheats.html)). They suit export adapters, not the core schema.

The gap all of these leave is typing for `.sym` (it carries no size or type) combined with bank-aware addressing. The notes' own synthesis, which this report endorses, is: import/export RGBDS `.sym` for labels, use stable-retro type strings for typed variables, keep an explicit bank field, and emit stable-retro `data.json` so the toolkit slots into existing RL tooling. No existing JSON/YAML schema specific to Pokemon Red RAM, and no tool that auto-verifies an address table against the disassembly, was found in the research notes, so the project would be filling a real gap rather than duplicating one.

## NPC reading and the shared world map have a ready template

Live NPC state lives in two 16-slot tables: `wSpriteStateData1` at `$C100` (picture ID, movement status, image index, screen position) and `wSpriteStateData2` at `$C200` (grid Y/X, movement byte, original facing), 16 bytes per sprite with the player always sprite 0 ([wram.asm mirror](https://v10.next.forgejo.org/foster/pokered/src/branch/master/ram/wram.asm)). A 2024 pokered commit renamed offsets to constants such as `SPRITESTATEDATA1_PICTUREID`, so field names drift between versions, a concrete argument for pinning a commit. These tables hold only the current map, so a shared NPC map must merge two sources: static placement from the pret object files, and live movement from agents standing on each map. The object files are plain text: `warp_event x, y, DEST_MAP, dest_warp_id`, `bg_event x, y, TEXT_...`, and `object_event x, y, SPRITE_..., STAY|WALK, direction, TEXT_...` ([PalletTown.asm](https://raw.githubusercontent.com/pret/pokered/master/data/maps/objects/PalletTown.asm)). Show/hide state comes from the missable-object flags at `D5A6-D5C5` ([Data Crystal](https://datacrystal.tcrf.net/wiki/Pok%C3%A9mon_Red_and_Blue/RAM_map)). No ROM binary parsing is needed for Red/Blue; an asset bundle can be built from the `.asm` sources, though the notes did not confirm the `.blk` block and tileset binary formats.

For global coordinates, the established design is pokerl-map-viz from the PokemonRedExperiments ecosystem (MIT). Agents send WebSocket JSON with `coords` as `[x, y, mapId]` arrays plus metadata (`user`, `env_id`, `color`, `sprite_id`); the client converts to global tiles with an `assets/map_data.json` offset table (`[x + mapX - 217.5, y + mapY - 221.5]`, times 16 px) and draws interpolated per-agent sprites on a large Kanto image, expiring stale sprites after two minutes ([visualizer_live.js](https://raw.githubusercontent.com/PWhiddy/pokerl-map-viz/main/visualizer_live.js), [pokerl-map-viz](https://github.com/PWhiddy/pokerl-map-viz)). Interior placement in any world map is a heuristic, not in game data: Vjeux built his 7,200 px Red/Blue map by walking map connections and matching warp doors to mats, then adjusting by hand ([Vjeux](https://blog.vjeux.com/2023/project/pokemon-red-blue-map.html)), so a hand-corrected `map_id -> (x, y)` table is the realistic approach. NPCs can share the same transform as agents. Ironmon Tracker (Gen 3 only, BizHawk/mGBA Lua) adds an architecture lesson: split Memory, per-version GameSettings (JSON address files since v9.0.0), Program and Drawing modules, with an extension API ([Ironmon-Tracker](https://github.com/besteon/Ironmon-Tracker), [Version Changelog](https://github.com/besteon/Ironmon-Tracker/wiki/Version-Changelog)); a Gen 1 BizHawk script serves party data as JSON over local HTTP, confirming that the viewer can be a separate process ([pokemon-memory-reader mirror](https://gh.r-mj.com/NathanTBeene/pokemon-memory-reader)). Polished Map edits Gen 1/2 map blocks and events but is an editor, not a runtime reader ([polished-map](https://github.com/Rangi42/polished-map)); Porymap is Gen 3 only ([porymap](https://github.com/huderlem/porymap)). No ready-made stitched full-world PNG with a known licence was found other than the community map used by pokerl-map-viz.

## Writing is the frontier: link battles, trades and opponent injection

PyBoy 2.9.0 has the primitives for this: `memory` indexing, `hook_register`, `save_state`/`load_state`, `symbols`, and constructor parameters `serial_shared_memory` and `serial_interrupt_based` ([PyBoy API](https://docs.pyboy.dk/api/pyboy.html)). Its experimental example `gamewrapper_pokemon_link_trade.py` links two instances through a shared-memory serial cable: one `SerialSharedMemoryBuffer`, player 1 in a `multiprocessing.Process`, both built with interrupt-based serial, headless supported, driving the Cable Club trade menu by reading `tilemap_window` text ([link trade docs](https://docs.pyboy.dk/wiki/examples/pokemon-link-trade.html), [example script](https://raw.githubusercontent.com/Baekalfen/PyBoy/master/extras/examples/gamewrapper_pokemon_link_trade.py)). The same script sets up parties with `pokemon.add_pokemon`, `set_event_flag` and `warp`, which is existing in-repo evidence that party writing works. Two constraints matter: save states are unsupported on linked instances (the script ignores the resulting exception), and the example covers trade only. **No published project automates a Gen 1 Colosseum battle between two emulated agents.** Whether the Colosseum path works over the same serial layer is a reasonable inference but untested, and the notes could not confirm which PyBoy release introduced serial support. The Gen 1 link RNG is documented: one side generates an array of random values (10 generated, 9 used, values at or above 253 rejected because `$FD` is the preamble), then each use takes the next value, after which values follow `x*5+1 mod 256` ([Smogon RBY link RNG](https://www.smogon.com/forums/threads/rng-in-rby-link-battles.3746779)). That supports deterministic lockstep between two PyBoy instances. Exact master/slave handshake bytes and on-wire party layout were not found; the notes direct reading `home/serial.asm` in pret/pokered, with `Serial_ExchangeBytes()` and the `$FD` preamble as the entry points ([DeepWiki pokeyellow](https://deepwiki.com/pret/pokeyellow/6.1-link-cable-system), secondary and seen only as a snippet). Alternatives are weaker: SameBoy exposes serial callbacks and a libretro two-player subsystem ([SameBoy issue 18](https://github.com/LIJI32/SameBoy/issues/18)), BizHawk is only reported by forum posters to support GB link, and mGBA's link is local-only with no Python two-instance example found ([mGBA forum](https://forums.mgba.io/showthread.php?tid=424)).

Opponent injection into a single emulator has precedent in technique but not in a PyBoy recipe. `read_trainer_party.asm` zeroes the enemy party count before reading the trainer table, so injected data must be written after that routine runs or it is overwritten ([read_trainer_party.asm](https://v10.next.forgejo.org/foster/pokered/src/branch/master/engine/battle/read_trainer_party.asm)); PokemonRedBlue-RAMdomizer demonstrates the timing technique by substituting enemy trainer data in WRAM every frame ([RAMdomizer](https://github.com/NPO-197/PokemonRedBlue-RAMdomizer)). In PyBoy, `hook_register` on the symbol following the party load is the natural equivalent; the enemy party region is near `D89C-D9ED` per Data Crystal, but the notes did not retrieve `wEnemyParty` from the symbol file and flag the address as unconfirmed. A static alternative is a ROM built from pokered with modified `data/trainers/parties.asm` tables; the notes recommend it as lowest-risk but unsourced. Single-instance injection yields a scripted in-game AI, not a second agent's choices, unless enemy move selection is also hooked. For search- and training-heavy work, pkmn/engine is a purpose-built Gen I/II simulator claimed to be frame-accurate, bug-for-bug and over 1000x faster than patched Showdown, with C, JS/WASM and Zig interfaces, though its main branch is breaking and cartridge accuracy was not independently verified ([pkmn/engine](https://github.com/pkmn/engine)). Gen 1 damage and critical-hit references exist in Smogon's articles and the Showdown gen1 mod ([Smogon RBY crits](https://smogon.com/rb/articles/critical_hits)), usable as oracles against PyBoy runs.

## Recommended module shape and open risks

Three layers follow from the evidence. A generated address layer: a build step turns a pinned pokered `symbols` commit into `ram_map_<revision>.json` carrying name, bank, address, size and a stable-retro type string, with a ROM hash check on load and exporters for `.sym`, stable-retro `data.json`, RA notes and `.wch`. A reader layer: typed accessors for party, enemy party, battle structs, map position, event flags (borrowing the named-bit idea from puffer without its code) and the two sprite tables, emitting plain dataclasses. A bridge layer: JSON over a WebSocket or local HTTP in the pokerl-map-viz shape, so viewers and agents stay separate processes. Writers (party set, event flags, warp, opponent injection, link pairing) should sit in a distinct module, since PyBoy already provides the write primitives and the risk lives in timing and unsupported combinations, not in address discovery.

Open risks are concrete. Licences: pokemonred_puffer has none visible and pret/pokered's text was not retrieved (ROM data and assets are Nintendo/Game Freak IP regardless), Data Crystal is GNU FDL 1.2, and Continual Harness is CC BY-NC-SA 4.0, so treat these as reference, not code sources. Version drift: which pokered revision the `.sym` matches your ROM is unstated, and sprite field names changed in 2024. Unproven paths: Colosseum over PyBoy serial, injection timing, and `symbols=` loading of pokered `.sym`. Unread material: Bulbapedia structures, pokecrystal, the `map_data.json` contents, `home/serial.asm`, Cheat Engine tables, and tracker or overlay ecosystems beyond the few found.

## Conclusion

The research reframes the module's scope: the novel work is not reading RAM, where a dozen projects have converged on the same addresses and formats, but unifying three things that currently live in separate ecosystems, namely typed variable files (stable-retro), disassembly-derived labels (RGBDS `.sym`) and live multi-agent visualisation (pokerl-map-viz). A symbol-generated, bank-aware, type-annotated table that exports to all of those is a gap no surveyed project fills.

The write side deserves a time-boxed spike before design commitments. Three questions decide the architecture: whether PyBoy's serial cable can enter the Colosseum, since a no-save-state constraint rules out rollback for linked pairs; whether a symbol-addressed hook reliably overwrites the enemy party after the trainer load; and whether pkmn/engine should carry search and training while PyBoy demonstrates on the real cartridge. If the Colosseum spike succeeds, Trailswarm would be publishing something the public record does not currently contain.
